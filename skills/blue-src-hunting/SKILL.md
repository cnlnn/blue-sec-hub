# SRC Hunting

## Workflow

1. 从现有项目规则或用户给出的范围提取可测资产、禁止动作、账号要求和报告门槛；已有范围不重复询问。
2. 先理解产品、角色、业务对象和高价值动作，再选择技术路线。
3. 资产与接口发现使用 `blue-web-patrol`；专项方法使用 `blue-security-knowledge`；源码目标使用 `bug-hunter`。
   Payload 变体从本地目录按实际请求形状检索，不能把公共 payload 清单机械发送给全部
   参数，也不能用扫描器或 payload 命中替代真实影响验证。
4. 围绕异常做同控制器、同对象、同角色和同状态机的相邻测试，避免无止境浅层扫描。
5. 提交前使用 `blue-evidence-validation` 检查可重复性、受影响用户、真实影响、公开性、前置条件和替代解释；可从 `blue-security-knowledge` 的 claude-bug-bounty 精选材料借鉴身份复核、去重和报告结构。
6. 报告保留最小可复现请求、证据、影响、范围依据和具体修复建议；不要套用上游面向赏金的机械 `kill` 规则覆盖当前项目规则。

不要把信息性配置、无影响版本信息或未完成的漏洞链包装成高危结论。
