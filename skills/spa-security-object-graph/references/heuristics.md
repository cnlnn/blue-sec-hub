# Graph Heuristics

## 优先级

优先检查同时出现至少两个结构信号的端点：

| 结构信号 | 说明 |
|---|---|
| 状态变更方法 | `POST`、`PUT`、`PATCH`、`DELETE` |
| 对象字段 | ID、UUID、Key、Code、Version、State、Status |
| 限制字段 | Limit、Amount、Price、Balance、Quota、Duration |
| 控制条件 | 身份、所有权、租户、角色、成员、审批、资格、状态 |
| 敏感能力 | 管理、凭据、个人信息、资金、文件传输、执行、消息 |
| 跨功能关系 | 一个功能提供标识，另一个功能消费该标识 |
| 标识来源链 | 当前身份可达的生产者、语义别名与敏感消费者形成连续链 |
| 生命周期配对 | 创建/查询、启用/停用、发布/撤回、上传/处理、申请/审批 |

领域词命中只能提高优先级。没有命中预设领域词的写接口仍必须参与对象图构建。

## 字段来源

发送完整写请求前建立字段来源表：

| 请求字段 | 来源接口或页面 | 所有权 | 预期服务端校验 | 已观察校验 |
|---|---|---|---|---|
| 对象标识 | 列表、详情、URL 或运行时响应 | 本人/他人/公开 | 对象可见且属于当前主体 | unknown |
| 父对象或版本 | 上游对象详情 | 自有/共享/受限 | 父子关系与版本适用性 | unknown |
| 角色、租户或组织 | 当前会话或选择器 | 服务端派生/客户端选择 | 当前身份有权使用 | unknown |
| 金额、容量或数量 | UI 默认值或表单 | 客户端输入 | 服务端范围和业务规则 | unknown |
| 状态和生命周期 | 当前对象详情 | 服务端状态机 | 合法状态转换 | unknown |

## 证据强度

- `observed-value-reuse`：本次浏览器流量观察到响应值被后续请求复用；不保存原值。
- `attacker-reachable-producer`：本次当前身份能够从页面、响应或文档获得消费者所需标识。
- `semantic-identifier-alias`：同一值在不同页面或接口以不同业务字段出现；只保存字段关系和哈希。
- `shared-object-field`：调用点共享有意义的对象字段。
- `same-api-family`：端点共享稳定资源前缀。
- `same-feature-chunk`：端点位于同一受限距离的组件或模块。
- `keyword-co-location`：只有术语重合，属于弱线索。

不得把 co-location 单独表述为数据流。压缩成单行的 Bundle 使用字节偏移，不使用行距。跨 Chunk 最多追踪两跳弱证据。

## 动态搜索支点

从已发现端点向两侧扩展，而不是依赖固定业务清单：

1. 从请求字段搜索同名字段的列表、详情、选择器和历史接口。
2. 从状态变更动作搜索相反或后续生命周期动作。
3. 从路径资源名搜索同 API family 的读写端点。
4. 从响应字段搜索运行时后续消费者。
5. 从身份、租户和角色字段搜索会话与权限来源。
6. 从敏感能力搜索结果验证、审计记录和清理入口。

## 误报控制

- UI 隐藏路由仍可能被设计为 API 可访问。
- 公开列表可能是正常目录，必须检查其标识能否越过后续控制边界。
- 历史日志中的标识、人工提供的他人标识或随机值不能代替攻击者当前可达的生产者。
- 公开目录和正常文件上传必须证明超出预期公开范围、解析、存储、执行或授权影响后才能确认漏洞。
- 参数错误只证明路由和处理器可达，不证明授权绕过。
- 创建成功只有在明确账号预期资格后才能判断是否未授权。
- WAF 差异属于边界控制现象，服务端授权需要单独验证。
- 共享字段可能只是常见命名；高频字段不建立近乎全连接的图。
- 历史报告或静态 Bundle 中的关系必须用当前环境重新验证。

## 普适性检查

加入长期 Skill、词表或上游补充前确认：

- 内容不包含域名、IP、绝对接口路径、账号或目标 opaque ID；
- 规则描述的是结构、语义或证据门槛；
- 至少在两个不相关领域的脱敏 Fixture 上有效；
- 对不包含该领域词的写接口仍能提取和建图；
- 中文别名和英文别名映射到相同稳定概念 ID；
- 新别名不会改变既有证据等级或自动产生漏洞定论。

## 请求重建与验证（自 SKILL.md Workflow 下沉，原文逐字一致）

### 3. 结构证据优先

端点评分优先使用 HTTP 写方法、请求字段、共享标识、响应到请求的值复用、生命周期配对、跨命名空间关系和身份边界。领域词只加分，不能成为是否提取端点或生成图谱的硬门槛。

对每个状态变更端点回答：

1. 接收哪些对象标识、状态和限制字段？
2. 哪个列表或详情接口提供这些值？
3. 预期由哪种身份、所有权、租户、审批、资格或业务状态控制？
4. 服务端自行推导控制条件，还是信任客户端选择？
5. 哪个查询、详情、历史或控制接口能证明结果？

每个敏感消费者必须能回溯到当前身份可达的标识生产者。历史日志、报告中的对象值和
随机不存在值只能生成发现种子；没有当前生产者时建立 `waiting-prerequisite`，继续搜索
菜单、列表、详情、分页、创建响应和相邻控制器，不能提前结算。响应到请求的复用建立
producer -> random binding slot -> consumer 链；同一值以不同字段名、字典代码或页面参数
出现时记录 semantic alias。原值只进入 Runner 读取后删除的 `0600` lease，Manifest、
Capsule 和 Git 不保存原值或可穷举的普通哈希。

### 4. 重建真实请求

依次优先使用浏览器流量、source map 调用点、组件提交函数、API wrapper，最后才做受控推断。记录每个 Header、路径和 Body 字段的来源，复用前端实际基础路径和应用 Header 后再判断 `401`、`403` 或参数错误。

### 5. 最小扰动验证

真实跨主体对象所有权使用两个已授权账号验证；匿名边界、低权限功能、隐式主体绑定、
自有对象、受保护属性和业务状态不依赖第二账号。先做只读和故意不完整的写请求；状态
变更只使用最小规格、唯一标记、单次请求，并立即验证和清理。

严格区分：

- endpoint reachability；
- parameter validation；
- successful state change；
- unauthorized impact；
- downstream control。

HTTP `200` 不能单独证明后三项。

### 6. 输出攻击路径候选

```text
actor -> prerequisite object -> client-controlled fields -> state-change API
      -> resulting object/capability -> verification API/UI -> impact
```

列出预期规则、观测规则、字段来源、证据类型、请求响应、清理状态和置信度。
